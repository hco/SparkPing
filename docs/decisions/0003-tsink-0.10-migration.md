# Move Storage to tsink 0.10 and Migrate Old Data in the Background

**Status:** Accepted  
**Date:** 2026-10-20

## Context

In October 2026 every ping of a Home Assistant installation failed with
`socket create failed: No file descriptors available (os error 24)`.

tsink 0.5 keeps one file descriptor open per on-disk partition for the life of
the process. With 6-hour partitions and a 20-year retention, the instance had
1040 partitions, more than the container's soft limit of 1024 open files. Ping
sockets share that limit, so every ping failed. Flushes failed as well and left
empty partition directories behind. Unflushed data stayed in memory, the WAL
grew to 5.8 GB, and the log, which had no rotation and logged every failed
ping, grew to 15.5 GB. Nothing in the UI showed that anything was wrong.

tsink only fixes the descriptor problem from 0.10 on. 0.10 is a new engine with
a different on-disk format and cannot read 0.5 partitions.

## Decision

1. **Raise the soft open-files limit** to the hard limit at startup
   (`src/fd_limit.rs`; on macOS capped at `OPEN_MAX`).
2. **Rotate the log by size** (10 MB × 5 files by default, `logging.max_size_mb`
   / `logging.max_files`). Ping failures are logged when a target goes down or
   comes back, with a reminder while it stays down, not per failed ping.
3. **Use tsink 0.10.2** (`src/storage/open.rs`):
   - **No memory limit.** tsink counts memory-mapped segment bytes against
     `with_memory_limit`. The budget fills with on-disk data, and writers then
     wait for admission while holding shard locks, which livelocked the
     storage in tests.
   - `with_chunk_points(8192)`: the in-memory index of persisted data is about
     0.3 MB per day of data instead of 0.9 MB, and data is about 7 % smaller.
   - `WalSyncMode::Periodic(1s)`: fsync per insert was 11× slower. A crash
     loses at most the last second of pings.
   - 24-hour partitions: a chunk never spans partitions, so longer partitions
     keep the chunk count low. Late writes can reach back 8 days (the default
     number of open partitions per series).
   - Retention only when `database.retention_days` is set (add-on option
     `retention_days`). The default keeps all data, as before.
4. **Migrate 0.5 data in the background** (`src/storage/migration/`). Before
   tsink 0.10 opens the data directory, 0.5 partitions and WAL segments are
   moved to `legacy-v05/`, so 0.10 never sees them. The server and pings start
   right away, and a background thread copies the old data oldest first:
   - Partitions are read one at a time with `tsink_legacy::disk::DiskPartition`
     (one descriptor), without opening the old storage.
   - The WAL overlaps partitions in time and is merged in by timestamp.
   - A partition is deleted only after every series in it has at least as many
     points in the new storage. tsink deduplicates identical points, so a
     migration interrupted by a restart can safely repeat a partition.
   - Partitions that cannot be read are kept and retried on the next start.
     Directories without `meta.json` and with only empty files are leftovers
     of flushes that failed during the outage and are deleted.
   - The migration pauses when tsink's in-memory index grows faster than
     compaction shrinks it. On a Raspberry Pi with years of data the migration
     can therefore take hours.
   - The old crate is a temporary dependency (`tsink_legacy = "=0.5.0"`) and
     can be removed together with the migration once installations have
     upgraded.
5. **Use a tsink fork** (`[patch.crates-io]` to `github.com/hco/tsink`, pinned
   by commit). In 0.10.2, `FramedWal::reset_locked` released the writer lock
   before persisting the published high-water mark. A concurrent append wrote
   the same temporary file, the rename failed with ENOENT, and background
   fail-fast stopped the storage until restart. This happens in normal
   operation, not only during the migration. The fork holds the lock until the
   reset is done. Remove the patch once a fixed tsink release exists. Turning
   fail-fast off is no replacement: the WAL state would be inconsistent.
6. **Report health** (`src/health.rs`, `GET /api/health`, banner in the UI,
   log lines on change). With fail-fast, any background error in tsink makes
   the storage reject everything until restart, so this must be visible. The
   report covers a stopped or degraded storage, open files near the limit,
   ping results not being stored, and migration progress or failures.

## Consequences

**Easier:**
- The number of open descriptors no longer grows with the amount of data
  (covered by a test that runs with a soft limit of 24).
- Problems like the outage show up in the UI and log within minutes.
- Upgrading needs no manual step; history becomes visible as the migration
  progresses.

**More difficult:**
- No downgrade: once the migration has deleted old partitions, an older
  SparkPing cannot read the data.
- With unlimited retention, memory grows by about 100 MB of heap per year of
  data, and every start reads all chunk files to check their checksums. The
  resident memory (RSS) roughly equals the data size, mostly as file-backed
  pages that the kernel can evict. Monitoring tools that show RSS will report
  this as high memory usage. Setting `retention_days` bounds both.
- The heap grows during the migration and only shrinks after a restart; the UI
  recommends restarting when the migration is done.
- SparkPing depends on a tsink fork until the fix is released upstream.

---

## Alternatives Considered

### Option A: Stay on tsink 0.5 with a higher open-files limit
- Pros: No migration.
- Cons: Descriptors still grow with data; the limit only delays the outage.
  Flush failures and unbounded WAL growth remain.
- Why rejected: Postpones the problem instead of fixing it.

### Option B: Migrate synchronously at startup
- Pros: Simpler; no mixed state.
- Cons: Pings stop for the whole migration, which can take hours on a
  Raspberry Pi with years of data.
- Why rejected: Monitoring would be down for too long.

### Option C: Start fresh and drop old data
- Pros: Simplest.
- Cons: Loses years of history.
- Why rejected: History is the main value of the tool.
